## 一、项目定位与健康度

**一句话定位**：SciPal 是一个「以会话为单位的论文 RAG 问答系统」，而不是通用知识库——每篇 PDF 上传后经 MinerU 解析、分块、向量化，生成会话级 FAISS 快照，检索走 BM25+向量混合 + RRF + rerank，答案流式输出并强制携带可回跳的原文引用（`api/routes/documents.py:95-114` 提供 chunk→原文定位）。

规模：后端 113 个 py、约 9400 行，前端 55 个文件 6538 行，合计约 18700 行；16 个 HTTP 端点；68 个测试 2 秒跑完。

| 维度 | 评分 | 理由 |
|---|---|---|
| 架构 | 7/10 | 六层分包清晰，domain 事件与传输解耦（`application/events.py:11-47`、`api/streaming.py:21-35`）；但跨层契约无单一真值（消息 status 三处不一致），前端「单例 composable + props 透传」双轨 |
| 实现质量 | 5/10 | happy path 完整可用，异常路径普遍未闭环：取消不 close、落库无 shield、删除先于重建、并发无锁 |
| 测试 | 5/10 | 68 例/2s 说明单测轻、跑得快；但 0 个前端测试，grep 不到任何断连/并发/provider 中途失败用例，恰好是缺陷最密集的区域 |
| 文档 | 4/10 | wiki 04/05/06/08/09 与代码高度一致，质量很高；README 整体停留在半年前，wiki 07/10/11 把已完成能力列为缺口，且指错了 `.env` 路径 |
| 安全 | 5/10 | XSS 面近乎为零（无 v-html、markdown-it `html:false`）；JWT+bcrypt 健全；但配置静默失效会让鉴权旁路悄悄生效，另有跨账号前端残留、绝对路径外泄 |

**综合 5.2/10**：骨架是好的，工程纪律也在（分层、类型、配置集中），但「契约」和「异常路径」两块欠账明显，属于「能演示、不敢多租户上线」的状态。

## 二、技术架构与关键设计

启动链路：`main.py` 注册 auth/sessions/documents/chat 四个 router，lifespan 内拉起 SQLite（WAL + `busy_timeout=5000`，`storage/sqlite/connection.py:22`）与一个后台摄取线程（`worker/runner.py:87` 每轮 `list_runnable_jobs(limit=1)`）。

一次提问的完整路径：

1. `POST /sessions/{id}/messages` 返回 `StreamingResponse`，`application/chat.py:120-122` 校验会话归属；
2. `resolve_session_store` 取「active + ready」的索引快照，没有就轮询最多 10s（`config.py:43`、`session_index.py:28-53`）；
3. 写入 user 消息、读 history，再 `rag/answer.stream_answer`；
4. 检索：`policies.py:13` 固定 `strategy="hybrid"`，BM25 + dense 各取 8 → RRF(k=60) → rerank 取 8（`rag/retrieval/`）；
5. 生成：`model_client.py` 用 OpenAI SDK 流式调用 DeepSeek，**同步生成器**由 `run_in_executor` 逐个 `next()` 推进（`chat.py:76`），转成 6 类领域事件；
6. 落库 + `sources/done` 收尾。

索引是快照式的：候选快照构建成功才 promote，失败回滚（`application/indexing.py:198-225`），这一点比多数同类项目做得严谨。前端 `useChatStream` 累积 token、`api/sse.ts` 只做分帧、`markdown.ts` 把 markdown 转成组件树渲染，三层职责分明。

## 三、核心资产（值得保留）

- **传输层抽象**：领域事件 → SSE 映射二次校验，未知事件直接 `TypeError`，不会静默丢事件（`api/streaming.py:21-35`）。
- **流式协议契约**：检测 legacy/显式协议混用，显式协议缺 `sources` 直接报错（`chat.py:112-118`），避免「无引用的答案」。
- **快照式索引 + 回滚**：`indexing.py:198-225`，FAISS 不能原地删向量，用整库重建 + 原子 promote 解决。
- **路径穿越防护**：`documents.py:113-121` 用 `is_relative_to(data_dir())` 拦截任意文件读取。
- **XSS 防线**：`markdown.ts:18-22` `html:false` + 组件白名单渲染，全 src 零 `v-html`。
- **评测可复现**：`scipal_eval/configs.py:6-149` 四套 config set，`docs/wiki/09-evaluation.md` 与之一致，没有虚构指标。

## 四、问题清单

> P0/P1 均已二次读码复核；`status="stopped"` 一项在 `backend/.venv` 内实测复现 `ValidationError`。被 refuted 的「成功落库写在 try 内导致重复答案」已剔除（`chat.py:176` 实际在 try 之外）。

### P0

**1. 登出不清洗任何前端单例，同浏览器换账号可读到上一账号全部会话与引用**
- 现象：`AppShell.vue:136-139` 的 `handleLogout` 只 `logout()` 后跳转；`useAuth.ts:57-63` 只清 token/user；`usePaperChat.ts:15-20` 是模块级 `store ??=`；`usePaperReader.ts:108-118` 的 `reset()` 全仓无调用点。
- 证据：`usePaperChat.ts:15-20`、`useAuth.ts:57-63`、`AppShell.vue:136-139`、`useLibrary.ts:17`。
- 后果：换账号后 `AppShell.vue:92` 因 `sessions.value` 非空跳过初始化，侧栏直接渲染他人会话标题，聊天区渲染完整对话（含论文原文片段）；点开 404 后旧消息仍留在界面（`useSessionState.ts:111-113` 只 setError 不清空）。共用电脑上是实质越权读。
- 修复：`logout()` 内统一 `resetAll()`（清 messages/sessions/documents + abort 在途流）+ `useLibrary().invalidate()` + `usePaperReader().reset()` + `useSourcePreview().close()`。

### P1

**2. `status="stopped"` 不在响应模型枚举内，一次「停止生成」可让整个会话永久 500**
- 证据：`chat.py:208` 以 `status="stopped"` 落库，`messages.py:27` 允许三值，但 `api/schemas/session.py:24` 是 `Literal["complete","failed"]`，`routes/sessions.py:31-33` 把行原样塞进 `SessionSnapshot`。
- 实测：`PersistedMessage(..., status="stopped")` → `ValidationError: Input should be 'complete' or 'failed'`。
- 后果：该行一旦写入（取消分支与 GC 终结器竞态，确实会发生），此后每次 `GET /sessions/{id}` 都 `ResponseValidationError` → 500，刷新/切换即打不开该会话，且系统无删除单条消息的接口，只能弃用会话。
- 修复：`Literal` 补 `stopped`，并加 stopped 消息的快照 round-trip 测试。

**3. 文档让把 `.env` 建在仓库根，代码只读 `backend/.env`——照做等于没配，鉴权静默关闭**
- 证据：`config.py:11-13,101` 的 `project_root()` 实为 `.../SciPal/backend`，`env_file` 指向 `backend/.env`；`README.md:90-93` 写「仓库根目录的 `.env`：`cp backend/.env.example .env`」；`docs/wiki/08-configuration.md:8-9` 同样写错。实测仓库只有 `backend/.env`，根 `.env` 不存在。
- 后果：用户把 `DEEPSEEK_API_KEY`、`JWT_SECRET_KEY` 填到根 `.env` 后，pydantic-settings 完全不读 → 聊天 `RuntimeError`，`jwt_secret_key` 保持空串、`app_env` 回落 `development`，`security.py:40-45` 匿名旁路生效。**用户以为配了鉴权，实际全站无鉴权**。
- 修复：统一为 `backend/.env`（改 README/wiki），或让 `project_root()` 真正返回仓库根；启动时打印实际加载的 env 路径。

**4. embedding「远端→本地」逐次静默回退且索引不记录模型指纹，一次抖动即污染向量空间**
- 证据：`rag/embedding/__init__.py:29-47` 每次调用先 remote、任意异常回落 local；`index_snapshots` 表只有 path/status（`schema.py:276-286`），`vector_store.py:113-160` 只存 faiss+chunks；remote 是 8B 模型、local 是 0.6B（`config.py:23-31`）。
- 后果：A 文档远端成功、B 文档超时回落本地 → 两套向量写进同一 FlatL2；查询再降级即「用本地向量搜远端空间」，排序毫无意义但不报错，答案照常生成并附带「有效引用」。维度不同时才在 `vector_store.py:65-72` 报一个语义误导的 mismatch。
- 修复：快照元数据写入 embedding 模型名/维度，加载时校验；查询端禁止跨来源降级（宁可报错）。

**5. 上传先 `read()` 全文再校验大小，50 MiB 上限形同虚设**
- 证据：`api/routes/documents.py:43` `pdf_bytes = file.file.read()`；`application/documents.py:27-34` 的 `_validate_upload` 在其后调用。worker 端 `handlers.py:30` 又整份读入内存。
- 后果：任一登录用户发 2 GB multipart 即可撑爆单进程 uvicorn，全站不可用；而 `wiki/04-api.md:162` 恰恰写「校验顺序：大小→%PDF→会话」，与代码相反。
- 修复：先按 `Content-Length` 拒绝，再分块落临时文件并累计计数，全程不 `read()` 整份。

**6. 前端对任何流中断整请求重放，服务端在出 token 前已落 user 消息——重试必然制造重复问答**
- 证据：`useChatStream.ts:94-107` 最多 3 次 POST，`constants/chat.ts:3` 为 2 次重试；`chat.py:141` 在生成前已 `_persist_and_touch(..., "user", ...)`；请求体只有 `{content, regenerate}`，无幂等键（`api/chat.ts:17-25`）。
- 后果：一次网络抖动 = 3 条同文 user + 至多 3 条 failed assistant，且 messages 表无单条删除接口；`history_rewrite` 的 4 轮窗口被重复问题占满；重试开头 `useChatStream.ts:69` 清空 `assistant.text`，界面「先长出来又缩回去」。
- 修复：前端生成 `client_message_id` 随体下发，后端按唯一索引 upsert；仅在「0 token 前失败」时重试，已出 token 改为提示手动重试。

**7. 多 provider fallback 的 try 包住整个 yield 循环，中途失败会把下一模型的完整回答接在残句后**
- 证据：`model_client.py:163-185` 的 `try` 同时包住 `create(stream=True)` 与 `for chunk ... yield delta`，`except Exception` 无 `emitted` 判断、不 close 旧 response 就换 provider。
- 后果：DeepSeek 吐到 40% 断流 → 自动切 fallback → 客户端收到「前半段 A + 整段 B」的拼接答案，并以 `status=complete` 整体落库（`chat.py:176`），事后无法识别。默认 `llm_fallback_enabled=False`（`config.py:85`），但开启 fallback 正是该功能卖点。
- 修复：`emitted=True` 后禁止换 provider，直接 close 并抛错；仅建连失败才允许降级。

**8. PdfViewer 对同一 canvas 并发 render，快速翻页后整页白屏卡在错误态**
- 证据：`PdfViewer.vue:51-82` 只保存 `renderToken` 丢弃结果，不保存 `RenderTask`、不 cancel；`:72-75` 先改 canvas 尺寸再 `await pdfPage.render(...)`；`:116-121` 的 page watch 与 160ms 防抖 resize 都会重入。
- 后果：pdf.js 抛「Cannot use the same canvas during multiple render() operations」，被 `:77-81` 捕获后整块容器 `v-show` 隐藏，引用高亮层一起消失，只能再翻一页碰运气。
- 修复：保存 `renderTask`，重渲染前 `await renderTask.cancel()` 并忽略 `RenderingCancelledException`。

## 六、优先级路线图

**近期（1–2 周，止血，投入产出最高）**
1. `PersistedMessage.status` 补 `stopped`（一行改动，消除会话级 500）。
2. 统一 `.env` 到 `backend/.env`，启动打印生效路径。
3. 上传改流式校验，先看 `Content-Length`。
4. 前端 `logout` 清全部单例；请求加 `client_message_id`。
5. `PdfViewer` 保存并 cancel `RenderTask`。
6. DB 移出包目录到 `data_dir()`，`.gitignore` 加 `**/*.db*`。

**中期（1 个月，修结构性缺陷）**
7. 流式生命周期重做：`try/finally gen.close()` + 专用线程池 + `create_task` 落库 + SSE 心跳/防缓冲头。
8. 索引：删除后重建失败回落到「chunk 现场构建」，新增 `POST /sessions/{id}/reindex`；快照记录 embedding 指纹。
9. 并发：per-session `asyncio.Lock` 覆盖「删除→读历史→写答案」；regenerate 改「先写后删」。
10. worker 多并发 + 前端轮询预算 ≥ 后端上限 ×1.5，区分「排队/解析」。

**长期（季度，提升可运维性）**
11. 用 schema 生成取代手写文档真值：路由表、配置字段、测试清单由 CI 自动比对，禁止手写计数。
12. 前端状态收敛为 provide/inject 或 Pinia，删掉 4 层 props 通道与 `ChatWorkspace` 空壳。
13. 可观测性：token/cost 落库、请求追踪、失败分类指标。

## 七、结论

**分层和引用闭环是这个项目的真本事，但「契约没有单一真值 + 异常路径没人收尾」让它目前只适合单人演示：先修 `stopped` 枚举、`.env` 路径、上传 OOM、登出残留这四处，再谈多用户与横向扩展。**
